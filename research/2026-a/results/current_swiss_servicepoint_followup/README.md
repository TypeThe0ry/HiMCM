# Swiss service-point follow-up

**Admission: 0 records and 0 increase.** The national source can identify candidate passenger stops and operating-point attributes, but these observations do not establish the number of distinct eligible physical Zürich stops or their comparability with the existing VBZ 446 count. No primary input, count rule or model has been changed.

The [official service-point cookbook](https://opentransportdata.swiss/en/cookbook/masterdata-cookbook/servicepoints/) describes a service point as a geographical or virtual administrative, operational, commercial or technical entity. `stopPoint` denotes passenger boarding/alighting stops; `freightServicePoint` denotes freight access, and `trafficPoint` covers stops, freight and tariff points, so it is not a passenger-only filter. `stopPointType` includes ORDERLY, ON_REQUEST, ZONE_ON_REQUEST, TEMPORARY, OUT_OF_ORDER and UNKNOWN; `meansOfTransport` describes modes designed for the stop and is null if `stopPoint=false`, not proof of a particular day’s service. `operatingPointType` identifies non-timetable-relevant operating types; `operatingPointTechnicalTimetableType` provides operating purposes, including bus operating points and turning loops. Evaluate combinations, rather than interpreting an ID or a single broad type as a commercial passenger location.

The source documents `validFrom`/`validTo` as validity of a service version. Its actual-date export is valid today; full covers past and future versions, and timetable-years covers current and next timetable years. Status describes the official-name release process (DRAFT, IN_REVIEW, VALIDATED, WITHDRAWN, REVOKED); the source marks REVOKED irrelevant. Validity, status and observed service are distinct. A status alone does not establish passenger service on a particular date.

`parentSloid` and `parentSloidServicePoint` link boarding-area/area records to higher-level records, but the cookbook's Europaplatz example explicitly assigns tracks 1–2 to operating parent `ch:1:sloid:7082` and tracks 3–4 to `ch:1:sloid:4108`, whereas the commercial stop is `8504108`. Thus the parent field itself cannot identify or automatically merge operating parents into one commercial stop. The reviewed documentation provides this concrete counterexample, not a general boolean or exhaustive crosswalk that resolves all commercial grouping cases. External operator or authoritative commercial mapping evidence would be needed case by case; coordinate or name similarity alone does not establish equivalence.

The official [service-point-v2 catalogue](https://data.opentransportdata.swiss/en/dataset/service-point-v2) advertises actual-date, full and timetable-year CSV resources. A fresh CKAN `package_show` attempt returned HTTP 403 HTML, so this attempt did not resolve or download a current raw CSV; the previous direct CSV 404 was not repeated. The official [FOT stop-list description](https://opentransportdata.swiss/en/cookbook/masterdata-cookbook/bav-haltestellen-liste/) identifies its daily Atlas subset as including stops and timetable-relevant operating points and supports JSON/CSV exports. A bounded five-record request to its [JSON endpoint](https://data.oev-info.ch/api/explore/v2.1/catalog/datasets/stop-points-today/records?limit=5) returned 200: the saved response includes `number`, `numbershort`, `sloid`, `stop_type`, `status`, municipality and operating fields. It is a small inspection sample, not an export or a Zürich census. The official description advises Atlas API or the mobility platform datasets for routine machine retrieval. Atlas is described as API-accessible; API authentication, schema and a successful Atlas response were not independently tested here.

The national cookbook identifies `number` as DiDok code and `numbershort` as its short component. These are candidate identifier fields to investigate against the cantonal WFS `nhstid` and `diva_nr`; no transformation or reliable match has been established. The parent investigation reports official canton metadata that `nhstid` spans three identifier ranges and can be redundant, and railway stations and adjacent bus stops are separate records; this follow-up does not infer a complete crosswalk or physical uniqueness from numerical resemblance. Names and coordinates may help investigate individual witnesses, without establishing a city-wide equivalence rule.

Original HTTP bodies, URLs, UTC retrieval times, statuses, content types, byte counts and SHA-256 receipts reside in `data/current_swiss_servicepoint_followup/`. The original cantonal response is reused unchanged from `data/current_zurich_transport/`. Run `python3 research/2026-a/data/current_swiss_servicepoint_followup/check.py` from repository root; it checks source hashes and basic document/sample assertions and generates `verification.json` with a direct source-to-SHA mapping. It does not independently validate service eligibility, parent equivalence, city boundaries, or the 446 baseline.
